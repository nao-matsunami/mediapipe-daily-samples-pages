注目事例と何が面白いか

Notable example and why it matters

今日の注目は、Gesture Recognizer の Web guide が synchronous な `recognize()` / `recognizeForVideo()` と UI thread block の注意を明示している点です。ジェスチャ操作は結果カテゴリの精度だけでなく、入力fps、同一video frameの重複推論、UI側の処理時間、発火の安定化が体験を左右します。本命サンプル `Gesture Recognizer Frame Scheduler` は、実モデルをロードできる構成を持ちつつ、手動フレームだけでも目標FPS、skip、疑似block、latencyの関係を確認できます。

Today's notable point is that the Gesture Recognizer Web guide explicitly calls out synchronous `recognize()` / `recognizeForVideo()` calls and possible UI thread blocking. Gesture interaction quality depends not only on category accuracy, but also input FPS, duplicate inference on the same video frame, UI-side processing time, and trigger stabilization. The main sample, `Gesture Recognizer Frame Scheduler`, can load the real model while also letting the scheduler be tested with manual frames only.

表現・インタラクションのアイデア

Expression and interaction idea

サンプルは `Load MediaPipe model`、`Start camera`、`Start loop` を分離し、permission や CDN で失敗しても手動gestureで動くようにしました。latency meter は `1000 / targetFPS` を予算として塗り分け、予算超過時は Worker 化または fps 低下を提案します。派生の `Gesture Vote Command Router` では Open_Palm、Closed_Fist、Thumb_Up、Pointing_Up を直近フレームの投票で command に変換し、cooldown 中の抑制理由も表示します。

The sample separates `Load MediaPipe model`, `Start camera`, and `Start loop`, so it still works through manual gestures when permissions or CDN loading fail. The latency meter uses `1000 / targetFPS` as the frame budget and suggests workers or lower FPS when over budget. The derivative `Gesture Vote Command Router` converts Open_Palm, Closed_Fist, Thumb_Up, and Pointing_Up into commands through recent-frame voting and shows why triggers are suppressed during cooldown.

サンプルデータの可能性と組み合わせ

Possibilities unlocked by sample data and combinations

蓄積できるデータは、targetFPS、simulated UI block、run frames、skipped frames、last latency、gesture category、manual / MediaPipe source、vote window、minimum votes、cooldown、winner、command fire log です。これを Hand Landmarker の tracking confidence、Gesture Recognizer の category score、PerformanceObserver、Worker postMessage latency、camera resolution selector と組み合わせると、Web ML gesture UI の起動前診断から操作安定化までを一続きで検証できます。

The samples can accumulate target FPS, simulated UI blocking, run frames, skipped frames, last latency, gesture category, manual / MediaPipe source, vote window, minimum votes, cooldown, winner, and command fire logs. Combined with Hand Landmarker tracking confidence, Gesture Recognizer category score, PerformanceObserver, Worker postMessage latency, and a camera resolution selector, this can test Web ML gesture UI from startup diagnostics through interaction stabilization.

制作に使えそうな技術メモ

Production note

実装は静的HTMLから `@mediapipe/tasks-vision@1.0.1/+esm` を dynamic import し、`FilesetResolver.forVisionTasks()` と hosted `gesture_recognizer.task` で `GestureRecognizer.createFromOptions()` を呼びます。video loop では `video.currentTime` が変わらないフレームを skip し、`performance.now()` で推論と疑似blockを合わせた時間を測ります。次段では `recognizeForVideo()` を Worker に移し、main thread では描画と command routing だけを担当させるのが自然です。

The implementation dynamically imports `@mediapipe/tasks-vision@1.0.1/+esm` from static HTML, then calls `FilesetResolver.forVisionTasks()` and `GestureRecognizer.createFromOptions()` with the hosted `gesture_recognizer.task`. The video loop skips frames when `video.currentTime` has not changed and measures inference plus simulated blocking with `performance.now()`. The next step is to move `recognizeForVideo()` into a worker and keep drawing and command routing on the main thread.
