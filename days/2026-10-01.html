今日の重要トピック

  1. Gesture Recognizer の Web guide は `runningMode` を `IMAGE` / `VIDEO` に分け、静止画では `recognize()`、動画フレームでは `recognizeForVideo(videoFrame, timestamp)` を使う構成を示している。

    The Gesture Recognizer Web guide separates `runningMode` into `IMAGE` and `VIDEO`, using `recognize()` for still images and `recognizeForVideo(videoFrame, timestamp)` for video frames.

  2. JavaScript API では `recognize()` と `recognizeForVideo()` が同期的に結果を返すため、実アプリでは worker 化、重複フレーム skip、UI budget の監視が重要になる。

    The JavaScript API returns results synchronously from `recognize()` and `recognizeForVideo()`, so real apps need worker isolation, duplicate-frame skipping, and UI budget monitoring.

  3. `setOptions()` で running mode を変えられるが、静止画操作とライブ動画を細かく行き来する UI では、切替コストを払う頻度そのものを設計対象にしたい。

    `setOptions()` can change running mode, but UIs that jump between still-image actions and live video should treat the frequency of mode switching itself as a design surface.

  4. MediaPipe v1.0.0 release notes では JavaScript IIFE bundle や VisionTaskRunner の running mode cache が触れられており、Web Tasks の運用面が継続的に更新されている。

    MediaPipe v1.0.0 release notes mention JavaScript IIFE bundles and VisionTaskRunner running-mode caching, showing that operational Web Tasks details continue to evolve.

  5. 公式サンプルや `mediapipe-samples-web` は実接続の参照に使い、今日の公開カードは合成 gesture queue と timestamp lane の自作検証にした。

    Official samples and `mediapipe-samples-web` are used as integration references, while today's public cards are original synthetic gesture-queue and timestamp-lane prototypes.

注目事例と何が面白いか

Notable example and why it matters

今日の注目は Gesture Recognizer の結果カテゴリではなく、その手前にある runningMode と timestamp の運用です。公式 Web guide は静止画の `recognize()` と動画の `recognizeForVideo()` を明確に分け、API reference はどちらも同期的に結果を返すことを示しています。つまり、ブラウザ UI では「どのジェスチャーが出たか」だけでなく、いつ `setOptions()` を呼ぶか、どのフレームを捨てるか、遅れて返った worker 結果を採用するかが体験を左右します。

Today's notable angle is not the gesture category itself, but the running-mode and timestamp operations before and around it. The official Web guide clearly separates still-image `recognize()` from video `recognizeForVideo()`, and the API reference shows both returning results synchronously. In a browser UI, the experience depends not only on which gesture was recognized, but also on when `setOptions()` runs, which frames are skipped, and whether late worker results are accepted.

制作に使えそうな技術メモ

Production note

実接続時は Web setup guide の package / WASM path を固定し、`GestureRecognizer.createFromOptions` の初期化、`setOptions({ runningMode })`、`recognize()`、`recognizeForVideo(videoFrame, timestamp)` を明確に分けます。動画では同一 `video.currentTime` の再処理を skip し、worker へ送る場合は request id と timestamp を一緒に持たせ、最新表示済み timestamp より古い結果を破棄します。静止画クリックが連続する UI では、即時に VIDEO へ戻さず短い猶予を置く sticky policy が有効です。

When wiring a real model, pin the package / WASM path from the Web setup guide and keep initialization, `setOptions({ runningMode })`, `recognize()`, and `recognizeForVideo(videoFrame, timestamp)` as separate operational steps. For video, skip repeated `video.currentTime` processing; if using a worker, send request id and timestamp together and drop results older than the latest displayed timestamp. For UIs with bursts of still-image clicks, a short sticky policy before returning to VIDEO mode can reduce unnecessary switching.
