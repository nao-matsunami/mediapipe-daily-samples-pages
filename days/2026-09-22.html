Designing the Gesture Recognizer worker queue first

Google AI Edge の Web setup guide、Gesture Recognizer Web guide、Hand Landmarker Web guide、Gesture Recognizer task guide、MediaPipe releases、mediapipe-samples-web を確認し、同期的な `recognizeForVideo()` / `detectForVideo()` を camera loop で扱う前の自作サンプルを2本追加しました。本命は frame rate、推論 cost、queue 上限、stale window、drop policy を動かす worker queue tuner、派生は返ってきた結果を timestamp と confidence で accept / defer / reject に分ける stale result journal です。

注目事例と何が面白いか

Notable example and why it matters

今日の注目は、Gesture Recognizer を「認識結果を画面に出す demo」ではなく、camera loop と UI thread の間に置く scheduler として見ることです。公式 guide は video frame を timestamp 付きで処理する例と、同期呼び出しが UI thread を block する注意を出しています。ここを最初に設計すると、実モデルをつなぐ前に drop oldest / drop newest / main-thread 実行の違い、stale 結果を採用する危険、queue 上限の妥当性を検討できます。

Today's notable angle is treating Gesture Recognizer not as a result-display demo, but as a scheduler between the camera loop and the UI thread. The official guide shows timestamped video-frame processing and warns that synchronous calls can block the UI thread. Designing this layer first lets us compare drop-oldest, drop-newest, and main-thread policies, stale-result risk, and queue limits before connecting a real model.

表現・インタラクションのアイデア

Expression and interaction idea

本命サンプル `Gesture Worker Queue Tuner` は frame rate、inference cost、queue limit、stale window、policy を変えると、投入済み frame、accepted / dropped / stale、UI score が更新されます。派生の `Stale Result Journal` は結果が返ってきた後の処理だけに絞り、deadline と confidence floor を動かして、accept / defer / reject の判断がどう変わるかを journal と metrics で見せます。

The main sample, `Gesture Worker Queue Tuner`, updates submitted frames, accepted / dropped / stale counts, and UI score as frame rate, inference cost, queue limit, stale window, and policy change. The derivative, `Stale Result Journal`, focuses only on returned-result handling and shows how deadline and confidence floor affect accept / defer / reject decisions.

サンプルデータの可能性と組み合わせ

Possibilities unlocked by sample data and combinations

蓄積できるデータは frame timestamp、queue length、inference cost、result age、gesture label、confidence、drop reason、stale reason、UI score です。Gesture Recognizer、Hand Landmarker、Holistic Landmarker、ImageBitmap transfer、Worker、OffscreenCanvas、PerformanceObserver、IndexedDB、WebRTC stats、Playwright smoke test と組み合わせると、ブラウザや端末ごとの推論負荷を見ながら、UI が固まらない hand / gesture interaction の実装基準を作れます。

The samples can accumulate frame timestamps, queue length, inference cost, result age, gesture labels, confidence, drop reasons, stale reasons, and UI score. Combined with Gesture Recognizer, Hand Landmarker, Holistic Landmarker, ImageBitmap transfer, Workers, OffscreenCanvas, PerformanceObserver, IndexedDB, WebRTC stats, and Playwright smoke tests, this can become a practical standard for hand / gesture interactions that avoid freezing the UI across browsers and devices.

制作に使えそうな技術メモ

Production note

実装時は `@mediapipe/tasks-vision` の version と `vision_bundle.mjs`、WASM path、modelAssetPath を pin し、main thread では camera capture と表示だけを残します。worker へ送る frame は ImageBitmap にして、処理後に close する方針にします。`recognizeForVideo(videoFrame, timestamp)` / `detectForVideo(videoFrame, timestamp)` の前後で `performance.now()` を測り、結果には入力 timestamp、完了時刻、推論 cost、score を付けて UI へ返します。UI 側では deadline 超過の結果を表示に使わない guard が要ります。

For production, pin the `@mediapipe/tasks-vision` version, `vision_bundle.mjs`, WASM path, and modelAssetPath, leaving only camera capture and rendering on the main thread. Frames sent to the worker should be ImageBitmaps and closed after processing. Measure `performance.now()` around `recognizeForVideo(videoFrame, timestamp)` / `detectForVideo(videoFrame, timestamp)`, then return input timestamp, completion time, inference cost, and score to the UI. The UI should guard against displaying results that exceed its deadline.

In the derivative sample, set Deadline to 90 ms, increase Jitter, and raise Confidence floor to 0.70 to make the reject-vs-defer boundary visible.
