注目事例と何が面白いか

Notable example and why it matters

今日の注目は、Audio Classifier を「音を分類するだけの task」ではなく、連続マイク入力を ring buffer に入れ、解析窓と overlap を決め、同期 `classify()` のコストをどこで吸収するかという runtime 設計として扱うことです。公式 guide は Audio Classifier がリサンプリング、バッファリング、フレーミングを扱うこと、そしてマイク入力では同期実行が UI thread を block し得ることを明記しているので、Web Worker、queue、drop policy まで含めた試作が有用です。

Today's notable angle is treating Audio Classifier not merely as a sound labeling task, but as a runtime design problem: continuous microphone input enters a ring buffer, analysis windows and overlap are chosen, and the cost of synchronous `classify()` has to be absorbed somewhere. The official guide explicitly notes preprocessing such as resampling, buffering, and framing, and warns that microphone classification can block the UI thread, so it is useful to prototype workers, queues, and drop policies together.

In audio UI, the experience often depends less on the class name itself and more on when the result is accepted and how similar an event must be to count as the same sound.

制作に使えそうな技術メモ

Production note

実装時は `FilesetResolver.forAudioTasks()`、`AudioClassifier.createFromOptions()`、`AudioClassifier.classify(audioData, sampleRate)`、`AudioEmbedder.embed(audioData, sampleRate)`、`baseOptions.modelAssetPath`、`scoreThreshold`、`maxResults` を分けて計測します。実マイクでは `ScriptProcessorNode` より AudioWorklet を優先し、Float32Array chunk を worker に渡すか、worker 側で task を保持します。window が短いほど反応は速い一方で分類が揺れやすく、overlap が大きいほど安定しやすい一方で queue が伸びます。

For implementation, measure `FilesetResolver.forAudioTasks()`, `AudioClassifier.createFromOptions()`, `AudioClassifier.classify(audioData, sampleRate)`, `AudioEmbedder.embed(audioData, sampleRate)`, `baseOptions.modelAssetPath`, `scoreThreshold`, and `maxResults` separately. For real microphones, prefer AudioWorklet over ScriptProcessorNode and either transfer Float32Array chunks to a worker or keep the task in the worker. Shorter windows respond faster but wobble more; larger overlap stabilizes results but can grow the queue.
