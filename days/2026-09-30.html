注目事例と何が面白いか

Notable example and why it matters

今日の注目は Face Detector を「画面に枠を出す task」としてではなく、起動前のモデル選択と検出後のイベント設計に分けて扱うことです。公式情報では Web setup、WASM path、npm package、Face Detector task、MediaPipe release notes の JavaScript 更新がそれぞれ別の場所にあります。実アプリでは、近距離セルフィーなのか、遠めの会議室なのか、bbox だけ使うのか、crop を保存するのかで設計が大きく変わります。

Today's notable angle is treating Face Detector not just as a task that draws boxes, but as two design layers: pre-startup model selection and post-detection event policy. Official information about Web setup, WASM paths, npm packages, the Face Detector task, and JavaScript release changes lives in separate places. In real apps, the design changes depending on whether the scene is a close selfie, a farther meeting room, bbox-only metadata, or stored face crops.

制作に使えそうな技術メモ

Production note

実接続時は Web setup guide の `FilesetResolver.forVisionTasks` と package version を固定し、short-range / full-range の model path を設定値として UI に出します。`scoreThreshold` と `maxResults` は検出器の品質調整だけでなく、後段イベント数と bandwidth に直結します。GPU first にする場合でも初回起動や低性能端末の fallback を測るため、モデル作成、最初の detect、連続 detect の3つを別メトリクスとして持つと原因を切り分けやすくなります。

When wiring a real model, pin the package version and `FilesetResolver.forVisionTasks` path from the Web setup guide, and expose short-range / full-range model paths as visible configuration. `scoreThreshold` and `maxResults` tune detector quality but also directly control downstream event volume and bandwidth. Even with GPU-first startup, keep separate metrics for model creation, first detection, and steady detection to distinguish fallback and low-end device behavior.
