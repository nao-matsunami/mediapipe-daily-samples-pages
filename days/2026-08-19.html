detectForVideo の前にフレーム予算を決める Governor

A frame-budget governor before detectForVideo loops

Google AI Edge の Hand / Face / Object Web guides と公式 MediaPipe samples web を参考に、連続 `detectForVideo()` を何 fps で回すべきかを試す自作ミニサンプルを追加しました。カメラ FPS、推論コスト、Worker lane、キュー上限、adaptive skip を動かすと、UI thread ブロック、古いフレーム処理、drop の関係を 60 フレームのタイムラインで確認できます。

注目事例と何が面白いか

Notable example and why it matters

今日の注目は、MediaPipe Task の結果描画ではなく、結果を得る前段の「何 fps で推論を投げるか」を UI として扱うことです。公式 Web guide は `detectForVideo()` が同期実行で UI thread を塞ぎ得ると説明しているため、実アプリでは Worker、間引き、キュー上限、古いフレーム破棄の方針が必要になります。自作サンプルでは推論コストと jitter を動かし、古いフレームが積み上がる状況と、最新フレーム優先で drop する状況を見比べられます。

Today's notable angle is not rendering MediaPipe Task results, but treating the pre-result question, 'what FPS should inference run at?', as an interface. The official Web guides explain that `detectForVideo()` is synchronous and may block the UI thread, so real apps need policies for Workers, throttling, queue limits, and stale-frame dropping. The original sample lets you adjust inference cost and jitter, then compare stale-frame buildup with latest-frame-first dropping.

制作に使えそうな技術メモ

Production note

公式 guide の `requestAnimationFrame()` ループは入口として分かりやすい一方、毎フレーム同期推論を呼ぶと描画と入力の応答を巻き込みます。実装では `lastInferAt` で target fps を守り、Worker lane では pending queue を 1 本だけ処理、上限超過時は drop、adaptive skip 有効時は queue が伸びる前に推論投入を抑制します。実モデルに置き換える場合は、`detectForVideo(video, timestamp)` の前後で `performance.now()` を測り、median cost と jitter に反映します。

The official guide's `requestAnimationFrame()` loop is a clear entry point, but calling synchronous inference every frame can drag rendering and input responsiveness with it. The implementation keeps target FPS via `lastInferAt`, processes one pending job in the Worker lane, drops when the queue exceeds the limit, and suppresses new inference before the queue grows when adaptive skip is enabled. With a real model, measure around `detectForVideo(video, timestamp)` using `performance.now()` and feed the median cost and jitter back into the governor.

試すならこれ

If you try one thing

まず Worker lane をオフにして、median inference cost を 50ms 以上、target inference fps を 20fps 以上に上げ、main thread lane busy の状態を確認します。次に Worker lane と adaptive skip をオンにし、drop は増えても queue が短く保たれることを見ます。最後に Check tasks-vision CDN を押して、`@mediapipe/tasks-vision@0.10.35` と WASM resolver が到達可能かを確認します。

First turn Worker lane off, raise median inference cost above 50 ms and target inference FPS above 20 FPS, and observe the main-thread-busy state. Then turn Worker lane and adaptive skip on and confirm that the queue stays short even if drops increase. Finally press Check tasks-vision CDN to verify that `@mediapipe/tasks-vision@0.10.35` and the WASM resolver are reachable.
